## 6. IndexedDB 保存可靠性 — P2

- **问题**：检查 250ms debounce 是否可能丢失最后一次修改，确保保存状态准确。
- **修复要求**：检查全部经 debounce 的保存路径；确认页面关闭 / 刷新前最后一次修改不丢失（如在 pagehide / visibilitychange 时强制 flush，或对关键操作同步保存）；保存状态指示只在写入完成后显示“已保存”，写入中显示“保存中”，失败显示错误并可重试。
- **测试要求**：输入后 250ms 内关闭 / 刷新页面，验证最后一次修改仍在；异常时状态指示正确；连续快速修改不丢中间状态。
- **复现结果**：已复现：v5 代码中 saveUser() 用 clearTimeout + setTimeout 250ms debounce，全站无 pagehide / visibilitychange / beforeunload 的保存 flush；最后一次修改后 250ms 内关闭/刷新页面，待写入的 put 不执行，最后一次修改丢失。
- **完成状态**：已修复（浏览器实测通过，部分情形仅代码路径核查）
- **测试证据**：写入已抽成 flushSave()，pagehide / 页面隐藏 / 交卷等关键操作立即落盘，250ms 合并写入保留；状态栏改为诚实文案（有待写入显示「有未保存的修改（保存中…）」，事务完成才显示「已自动保存」）；连续快速修改后刷新，最终状态与最后一次修改一致；交卷后立即刷新，交卷状态、答案与归档全部保留。未实测：审计探针无法断开 IndexedDB，「断开数据库时状态指示」一项仅代码路径核查通过，未做浏览器实测。
- **复查后补充修复（2026-11-19，针对 commit e16de9e5）**：GPT 复查指出 savePending 与 doWrite() 的异步事务存在竞争：第一次事务完成后将 savePending=false，但第二次修改仍在 debounce 等待期间，关闭页面时最后一次修改没有被 flush。复现：旧逻辑在 node 中按竞争场景复现——第一次事务完成后 savePending=false、第二次修改仍在防抖等待，flushSave 未创建事务、落盘仍为旧值，丢失确认。修复：引入保存版本号 saveSeq——每次 saveUser() 调用版本号 +1，doWrite() 写盘时捕获当前版本号 const v=saveSeq，tx.oncomplete 时只有 v===saveSeq 才清除待保存标记并显示「已自动保存」，若 v<saveSeq 则不清标记、立即再执行一次 doWrite() 写最新数据；tx.onerror 与异常分支保持原样（savePending 保持 true 以便重试）；saveUser()、flushSave()、250ms 合并写入、pagehide/visibilitychange 接法均不变。测试：node 抽取站内修复后的真实 saveUser/doWrite/flushSave 函数配模拟事务队列逐项验证 14/14 通过——快速连续修改 3 次后立即 flush 落盘为最后一次修改；第一次事务进行中到达第二次修改、事务完成与 pagehide 同时发生时标记不被误清、补写事务立即发出、最终落盘为较新修改；等待/补写期间状态栏从不显示「已自动保存」；普通防抖保存、事务出错、无数据库三条路径行为与上一轮一致；全部 10 个 script 块 node --check 通过（修复前后各跑一次）。如实说明：事务完成与 pagehide 同时发生时点以模拟事务队列精确控制，未在真实浏览器以肉眼时序复现。完成状态保持已修复。
